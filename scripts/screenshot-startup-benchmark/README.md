# Fork macOS runner capability probe

This is preparation for a screenshot editor startup benchmark. It does not build Cap, measure startup, or satisfy the PR's macOS validation requirement.

The workflow runs only in `dovidmoishe/Cap`, on pushes to `perf/screenshot-startup-benchmark` that change these tools or their workflow. It uses standard GitHub-hosted `macos-15` (Apple Silicon) and `macos-15-intel` runners. It does not require Cap's Blacksmith account. This push trigger allows the initial run without adding the workflow to the fork's default branch. Existing runs can be rerun in GitHub Actions.

Keep this tooling on the benchmark branch. The production PR remains on `perf/screenshot-editor-startup`; do not merge this branch into it. After collecting evidence, commit and push only the production fixes from that PR branch and summarize the results in the PR description or a comment. Benchmark tooling does not need to accompany those fixes.

Each job opens an owned, borderless test window on the main display. The left third is red, the right third green, and the center starts magenta. It checks for a Metal device, clears and presents a window drawable in blue, and captures the full display through ScreenCaptureKit. The captured image must contain the red and green regions, and the center must contain the Metal-rendered blue region. Merely listing a GPU or returning a screenshot is insufficient.

The probe records partial results before potentially blocking operations. It fails if a display, visible window, completed Metal command, captured fixture, or captured GPU output cannot be verified. It has a 60-second in-app deadline, a 90-second process deadline, and a ten-minute job deadline. It does not grant permissions or modify the runner's permission database. A denied capture or missing graphics device is evidence that more runner setup or another runner is needed, not evidence of a Cap regression.

Uploaded diagnostics include the capability JSON, compile/runtime logs, OS and runner image versions, hardware information, and a display PNG. The display image is from the disposable CI runner, not the user's desktop. Artifacts expire after seven days. The workflow has only read access to repository contents, does not use repository secrets, and does not post PR comments or modify branches.

Resources live only for the probe process. The test window, Metal layer, and command queue are retained while capture runs and released when the process exits. No renderer resources are added to the production application.

A pass establishes basic AppKit, Metal presentation, and ScreenCaptureKit capability on that runner image. It does not establish GPUI/wgpu compatibility, permission for a separately built Cap binary, the fallback SCStream path, representative consumer hardware, or a flash-free preview handoff. The next step is a separate Cap smoke run, then matched baseline/revised release-build measurements on one runner with fixed capture input, separate first-use/warm samples, and separate preview/GPU draw endpoints. Transition recordings must run separately from timed samples.

Preparation on Windows can validate the workflow structure and Python runner, but cannot compile this macOS Swift program. The first Actions run must compile and execute it; until then its macOS behavior is unverified.

## Cap release smoke run

`fork-screenshot-cap-smoke.yml` is the next stage, on the same dedicated branch and only in the fork. It rechecks the capabilities of its own Apple Silicon runner, prepares the repository's native libraries and patched GPUI dependency, and builds baseline and revised Cap binaries sequentially using Rust 1.95.0 and the existing release profile. Compilation uses two jobs to limit memory pressure. The job has a two-hour limit; dependency caching is enabled for later runs, including when a smoke check fails. The runner has virtual graphics, so later results must be labelled as CI measurements.

`snapshots/source-manifest.json` pins upstream baseline `346561b837aaa2cd27eea01b90b858d6596848b5`, identifies the production parent commit, and hashes the baseline and revised source files. `snapshots/revised.patch` contains only the three production Rust files changed by the PR's current local revisions. It includes removal of the optional hidden-window and warm-layer experiments, conditional retention of RGBA pixels, the settings snapshot, and the existing startup/stale-frame fixes. It contains no measurement hooks. The patch omits context lines and is guarded by exact source hashes; line endings are normalized so Windows and macOS checkouts produce the same checksum. The production revisions are a snapshot of uncommitted work, not a claim that those changes were already pushed to the PR.

`build-cap.py` verifies those hashes, applies the revised patch only when building the revised binary, and injects identical draw instrumentation into both variants. It restores the checkout's four source files afterward. The start hook runs at screenshot capture entry. The image element is replaced with an equivalent image-paint canvas that records its first visible paint followed by a GPUI frame callback. The GPU result is marked separately so the revised raw preview cannot be mistaken for completed GPU rendering. This software endpoint does not measure physical scanout. After the GPU callback, the hook waits six seconds and closes the editor through its normal native close handler. These hooks exist only in the benchmark checkout and its instrumented binaries.

Both workflows explicitly use GitHub's Bash shell with pipeline failure propagation, so a failed command cannot be hidden by a successful `tee`. They also check that compiled helpers exist and are executable. Before building Cap, the smoke workflow runs the fixture's PNG decoder against the successful capability probe's captured display and verifies the expected colors. The decoder loads file bytes into `NSBitmapImageRep(data:)`; macOS compilation and this decoder check must pass before the expensive Rust build begins.

`cap-fixture.swift` owns a fixed full-display red/blue/green test window at level 101, above Cap's main panel at level 100. Cap uses an isolated profile and settings file with onboarding completed and the normal open-editor action. After Cap saves the captured PNG, an IPC signal tells the fixture to hide. The first draw callback must occur at least 25 ms after the fixture hides. The saved screenshot must match the display dimensions and fixture colors. A separate ScreenCaptureKit image of Cap's owned editor must show those colors, and Cap must log its normal editor-close callback. Baseline and revised saved PNG hashes must match. Child processes are terminated only after the normal editor-close check, or on failure; the fixture and app use no personal profile.

One capture per version is a smoke test, not a performance comparison. External image recording and validation are enabled; reported draw times are diagnostic only. This does not verify that a preview transition is flash-free, nor cover repeated captures, exports, or clipboard behavior. Artifact upload is attempted after an earlier step fails, excluding the executables; a hard cancellation or job timeout can prevent upload. Artifacts expire after seven days. If this passes, repeated timing samples and a separate transition check can be prepared without changing the production PR branch. Refresh the source snapshot and revalidate affected results if production code changes afterward.
