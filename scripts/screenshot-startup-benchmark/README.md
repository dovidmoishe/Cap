# Fork macOS runner capability probe

This is preparation for a screenshot editor startup benchmark. It does not build Cap, measure startup, or satisfy the PR's macOS validation requirement.

The workflow runs only in `dovidmoishe/Cap`, on pushes to `perf/screenshot-startup-benchmark` that change these tools or their workflow. It uses standard GitHub-hosted `macos-15` (Apple Silicon) and `macos-15-intel` runners. It does not require Cap's Blacksmith account. This push trigger allows the initial run without adding the workflow to the fork's default branch. Existing runs can be rerun in GitHub Actions.

Keep this tooling on the benchmark branch. The production PR remains on `perf/screenshot-editor-startup`; do not merge this branch into it. After collecting evidence, commit and push only the production fixes from that PR branch and summarize the results in the PR description or a comment. Benchmark tooling does not need to accompany those fixes.

Each job opens an owned, borderless test window on the main display. The left third is red, the right third green, and the center starts magenta. It checks for a Metal device, clears and presents a window drawable in blue, and captures the full display through ScreenCaptureKit. The captured image must contain the red and green regions, and the center must contain the Metal-rendered blue region. Merely listing a GPU or returning a screenshot is insufficient.

The probe records partial results before potentially blocking operations. It fails if a display, visible window, completed Metal command, captured fixture, or captured GPU output cannot be verified. It has a 60-second in-app deadline, a 90-second process deadline, and a ten-minute job deadline. It does not grant permissions or modify the runner's permission database. A denied capture or missing graphics device is evidence that more runner setup or another runner is needed, not evidence of a Cap regression.

Uploaded diagnostics include the capability JSON, compile/runtime logs, OS and runner image versions, hardware information, and a display PNG. The display image is from the disposable CI runner, not the user's desktop. Artifacts expire after seven days. The workflow has only read access to repository contents, does not use repository secrets, and does not post PR comments or modify branches.

Resources live only for the probe process. The test window, Metal layer, and command queue are retained while capture runs and released when the process exits. No renderer resources are added to the production application.

A pass establishes basic AppKit, Metal presentation, and ScreenCaptureKit capability on that runner image. It does not establish GPUI/wgpu compatibility, permission for a separately built Cap binary, the fallback SCStream path, representative consumer hardware, or a flash-free preview handoff. The next step is a separate Cap smoke run, then matched baseline/revised release-build measurements on one runner with fixed capture input, separate first-use/warm samples, and separate preview/GPU draw endpoints. Transition recordings must run separately from timed samples.

Preparation on Windows can validate the workflow structure and Python runner, but cannot compile this macOS Swift program. The first Actions run must compile and execute it; until then its macOS behavior is unverified.

## Cap release smoke run

`fork-screenshot-cap-smoke.yml` runs three sequential jobs on the dedicated branch and only in the fork. Python is pinned to 3.13. First, a ten-minute validation job compiles the Swift helpers, downloads the five investigated PNGs from run `39426190700`, tests the checker against those images and synthetic controls, checks packaging failure paths, and verifies graphics/capture capability. Failure blocks the Rust build. If the source artifact expires, this gate fails cheaply; replace it only with explicitly reviewed equivalent evidence.

The build job prepares the repository's native libraries and patched GPUI dependency, then builds baseline and revised binaries sequentially using Rust 1.95.0 and the existing release profile. Compilation uses two jobs to limit memory pressure and a 100-minute job limit. Dependency caching is enabled, but release linking can still be expensive. The final job runs on a fresh Apple Silicon runner with no native-dependency setup and no Cargo invocation. It now has a twenty-minute limit for the smoke check plus repeated measurements. The runner has virtual graphics, so results must be labelled as CI measurements.

`snapshots/source-manifest.json` pins upstream baseline `346561b837aaa2cd27eea01b90b858d6596848b5`, identifies the production parent commit, and hashes the baseline and revised source files. `snapshots/revised.patch` contains only the three production Rust files changed by the PR's current local revisions. It includes removal of the optional hidden-window and warm-layer experiments, conditional retention of RGBA pixels, the settings snapshot, and the existing startup/stale-frame fixes. It contains no measurement hooks. The patch omits context lines and is guarded by exact source hashes; line endings are normalized so Windows and macOS checkouts produce the same checksum. The production revisions are a snapshot of uncommitted work, not a claim that those changes were already pushed to the PR.

`build-cap.py` verifies those hashes, applies the revised patch only when building the revised binary, and injects identical draw instrumentation into both variants. It restores the checkout's four source files afterward. The start hook runs at screenshot capture entry. The image element is replaced with an equivalent image-paint canvas that records its first visible paint followed by a GPUI frame callback. The GPU result is marked separately so the revised raw preview cannot be mistaken for completed GPU rendering. This software endpoint does not measure physical scanout. After the GPU callback, the hook waits six seconds and closes the editor through its normal native close handler. These hooks exist only in the benchmark checkout and its instrumented binaries.

The workflows explicitly use GitHub's Bash shell with pipeline failure propagation, so a failed command cannot be hidden by a successful `tee`. They also check that compiled helpers exist and are executable. The decoder loads file bytes into `NSBitmapImageRep(data:)`. The previous probe-only decoder check missed the actual rejection: on the saved Cap images, `colorAt` followed by device-RGB conversion changed the blue stripe's green value from `75/255` to `0.40019059`, failing a `< 0.4` predicate. Run `39421998519` reproduced that conversion for baseline and revised images.

The fixture checker now uses stored, opaque, eight-bit RGB samples with the same thresholds. Unsupported formats or transparent sampled pixels cannot count as fixture colors. Converted device-RGB center values remain in the evidence. This identifies the test scene; it does not establish colorimetric accuracy. `validate-images.py` tests all five saved PNGs, blank/swapped/missing-color/transparent/grayscale controls, sparse center-only colors, a one-channel interior change, and the exact 16-pixel exclusion boundaries. Real Swift decoding and comparisons run on macOS before Cargo; Windows checks cannot substitute for them.

Run `39426190700` passed the decoded-image controls and built, packaged, and launched both variants, but the live editor bitmap did not satisfy the checker's raw-format/opacity requirements. The saved editor PNG contains the expected opaque RGB samples. Both the live capture evidence and `--inspect-image` now use the same `pngEvidence` function to decode the saved PNG bytes before inspecting them. This removes the separate untested live-bitmap inspection path. The extra decoding runs only during smoke evidence collection, not in production or timed samples. The current preflight reproduces that run's 36 border differences with zero interior differences; the fixed 16-pixel comparison boundary is unchanged.

`cap-fixture.swift` owns a fixed full-display red/blue/green test window at level 101, above Cap's floating main panel on macOS. Cap uses an isolated profile and settings file with onboarding completed and the normal open-editor action. After Cap saves the captured PNG, an IPC signal tells the fixture to hide. The first draw callback must occur at least 25 ms after the fixture hides. The saved screenshot must match the display dimensions and contain substantial fixture color regions. A separate ScreenCaptureKit image of Cap's owned editor must show those colors, and Cap must log its normal editor-close callback. Child processes are terminated only after the normal editor-close check, or on failure; the fixture and app use no personal profile.

Baseline and revised stored RGB must match exactly throughout the interior after excluding a fixed 16-pixel border on all four sides. Both captures still cover the full display. Run `39415518245` had eight different pixels near the upper-right indicator, with a maximum channel difference of one; this predetermined exclusion accommodates that region. The comparison reports an interior hash for each input, the interior mismatch count, and every border difference with its coordinates and values. It rejects unsupported pixel formats and dimension mismatches. Full PNG files and their hashes are retained. This is weaker than full-image equality and does not validate the excluded edges; disclose the exclusion in any later performance report.

One capture per version is a smoke test, not a performance comparison. External image recording and validation are enabled; reported draw times are diagnostic only. This does not verify that a preview transition is flash-free, nor cover repeated captures, exports, or clipboard behavior. Validation values and helper logs are saved before assertions where available. Evidence upload is attempted after failures; a hard cancellation or job timeout can prevent upload. If this passes, repeated timing samples and a separate transition check can be prepared without changing the production PR branch. Refresh the source snapshot and revalidate affected results if production code changes afterward.

## Reusable runtime package

`bundle-cap.py` packages both executables, instrumented sources, source provenance, FFmpeg frameworks/libraries, and ONNX Runtime. Runtime symlinks are dereferenced so copied paths do not point back to the build checkout; this costs archive space. It records executable/source/file checksums, executable permissions, the fork commit/run, and `otool -L` output. A tar archive preserves modes. Its checksum and file manifest are verified after safe extraction, and source/run provenance is checked before launch. Checksums detect damage and mismatched artifacts; they are not an independent signature of trusted code.

The `cap-screenshot-runtime-macos-15` artifact is uploaded before smoke testing. The fresh test runner downloads it from this fork, extracts it under a different path, and sets framework, library, and ONNX paths to the package. Original checkout runtime directories must be absent. Dynamic library loading is logged. A successful smoke run therefore also verifies that these screenshot paths launch from the extracted package. It does not test every lazily loaded media feature.

`reuse-build-run.txt` contains `build` for a new build. For an artifact-only retry, change it to the numeric ID of the fork run that uploaded the package. The next branch push runs validation, skips the build job, and downloads that run's package. The package must still exist, match the selected fork run, and contain the current production snapshot and measurement instrumentation. Artifacts expire after seven days. Keep or download the package before expiry if further checks are needed. Old failed runs excluded the binaries and cannot supply this package.

## Repeated timing run

The workflow, now named `Fork Cap screenshot benchmark`, runs `run-benchmark.py` immediately after a successful smoke check on the same runner. `reuse-build-run.txt` remains pinned to `39426190700`, so this reuses the release binaries verified by smoke run `39432866187`; neither the Rust sources nor measurement instrumentation change. Validation also runs `test-benchmark.py` before the runner can start timed samples.

There are two additional warmup captures per variant, then twelve measured pairs. Pair order alternates baseline/revised and revised/baseline, giving each variant six first positions among measured pairs. Each capture starts a fresh process and isolated profile. File hashing, preceding smoke captures, and warmups leave filesystem and driver caches warm. This does not measure a cold machine or repeated editor opens within one app process. No outliers are removed, and a failed capture stops collection instead of being silently excluded.

The shared capture runner uses `capture_editor=False, desktop=True` for timings. This disables the editor PID request and verbose dynamic-loader logging and launches a windowless helper with prohibited activation policy. There is no colored overlay above the timed editor. The colored fixture and its original 25 ms exposure guard remain only in the separate smoke check. Capture-completion IPC, log polling, identical draw hooks, and automatic close six seconds after the GPU callback remain enabled in both variants. PNG inspection occurs after normal editor close. Warmup inputs must match exactly throughout the fixed interior before any measured samples start; measured inputs are checked after collection against the same first-warmup reference. All excluded border differences are retained. A failed comparison invalidates performance results for the whole run; the comparison region is not enlarged to accommodate desktop changes.

The runner reads the native window number from Cap's `main window opened number=...` log and atomically publishes `desktop-request.json` with that number and the owned process ID. The desktop helper must observe an on-screen Window Server record matching both fields before it calls `NSRunningApplication.hide()` once. It verifies that the app is hidden and that specific window remains off-screen for at least 250 ms. No window level is used to select or validate the main panel. Run `39483468319` exposed an incorrect level-100 assumption: Cap's macOS main window uses `NSFloatingWindowLevel`, while `MAIN_WINDOW_LEVEL` applies to other platforms at that call site. That run stopped during its first warmup and yielded no valid performance comparison.

The helper records the hide return value but does not treat `false` as an immediate failure: native diagnostic run `39481160622` observed successful hiding and reopening in all four regular-app cases despite that return value. Accessory-app cases did not satisfy the same checks; the helper records the actual activation policy and requires observed hiding rather than assuming support. Preparation has a three-second timeout with intermediate state, visible window numbers, and layers saved to `desktop-state.json`. It writes the PID, main-window number, observation flag, request count, return value, activation policy, stable-hidden duration, and UTC completion time, then invalidates its timer so it cannot re-hide the editor. The runner requests preparation 400 ms after observing the main-window startup log, allowing initial activation to finish. Validation checks the reported identity against the startup log again. Preparation must complete at least 250 ms before the capture-entry timestamp. A failure is rejected rather than subtracted from the measured latency. This measures the shortcut flow with Cap initially hidden, rather than capturing a visible Cap main panel.

`test-desktop-setup.py` runs before timing and in the initial validation job. It starts only owned helper processes: a windowless controller and a stand-in `NSPanel` at `.floating` level with `hidesOnDeactivate` disabled. It verifies that the stand-in's AppKit window number identifies its owned on-screen Window Server record before sending the identity request. It verifies hiding, then asks the stand-in to open and activate a normal editor window and confirms it becomes visible without interference from the controller. No Cap compilation is needed. Windows tests simulate the runner protocol, including missing/ambiguous startup numbers, invalid request identities, wrong PIDs or window numbers, missing/late preparation, visible panels, very fast preview callbacks, input drift, and preservation of the colored smoke mode. Actual AppKit hiding and the new helper's Swift compilation require macOS CI.

The start is the existing `Instant` at `take_screenshot` entry, before settings/device preparation and capture-window preparation; the two endpoints remain first visible image paint plus a GPUI next-frame callback, and first GPU-result image paint plus that callback. These software events do not establish physical scanout. The baseline's first image already comes from the GPU; the revised image can use the raw preview sooner. App launch, hiding, and the automatic-capture delay precede the timer. Optional screenshot startup experiments are removed from the process environment. The input is the actual CI desktop, so results do not represent every screenshot content or PNG encoding cost. Run `39437204432` used the old colored-overlay method and failed after seven complete measured pairs when its exposure margin fell to 14.6 ms; that incomplete dataset is not a valid performance result and is not combined with desktop samples.

The artifact's `timings/` directory contains every sample's profile, original PNG, logs, capture checks, and normal-close evidence; `samples.csv`; partial and final JSON; input comparisons; build/source/runner provenance; and `report.md`. The report gives median, nearest-rank p90, min/max, median paired reduction, and the number of pairs in which the revised version is faster, separately for preview and GPU output. A negative reduction is reported as slower. Partial failures retain evidence but produce no performance summary. The collector has a fifteen-minute deadline within the twenty-minute job limit.

Benchmark numbers describe the recorded macOS CI version, virtual GPU, display dimensions, release profile, source snapshot, sample count, and warmup conditions. They do not establish consumer Mac performance, a flash-free preview handoff, exports, or clipboard correctness. The transition check still requires a separate untimed recording run.
