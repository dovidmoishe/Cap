# Screenshot preview-to-GPU evidence

This is a fork-only, untimed visual diagnostic for the GPUI screenshot editor. It does not rebuild Cap, change production sources, or replace the completed timing run `39488846038`. It reuses the release package from `39426190700` and verifies its files, executable permissions, source snapshot, and instrumentation provenance before launch.

The separate `Fork screenshot transition evidence` workflow triggers only for this directory or its own workflow file on `perf/screenshot-startup-benchmark`, and only in `dovidmoishe/Cap`. These commits stay out of the production PR branch. It contains no Cargo build or repeated benchmark step.

## Recording flow

The native helper opens a static red/blue/green and grayscale background panel at level -1, below normal windows. It does not activate the app or hide itself during the handoff. Cap's main window is hidden using the existing owned PID/window-number protocol before display capture. The editor opens above the pattern. The source PNG must contain the pattern, so a blank desktop does not qualify as useful color evidence.

ScreenCaptureKit starts before Cap launches, requests 60 updates per second, and captures the full display without a pointer or audio. The helper confirms that its own pattern is actually visible in captured pixels before the runner can launch Cap. Acquisition is restricted to a scale-one display; other configurations are unverified and rejected.

An 8×8 grayscale marker in the top-left corner changes at a requested 60 Hz to keep a static desktop producing actual complete frames. It is a separate nonactivating panel above the menu bar. Readiness requires observing at least three distinct grayscale values in captured pixels, and analysis rejects a marker rectangle that overlaps the editor. This changes a small part of the captured source and adds diagnostic rendering load. The source marker captured by Cap is frozen in the screenshot; only the live marker outside the editor continues changing. These conditions apply only to this untimed recording, not the completed benchmark.

ScreenCaptureKit's queue depth is three. Complete BGRA buffers are copied to temporary disk; idle events reference the previous stored pixels because the API reports that the display did not change. The recorder keeps the full event history without eviction, with limits of 2,400 events, 64 MiB per frame, and 4 GiB of raw disk data. Reaching a limit makes the evidence inconclusive instead of discarding the early preview. At 1024×768 and 60 complete frames per second, 20 seconds uses about 3.5 GiB of raw data. Only the latest pixels and a temporary copy need remain in recorder memory; framework buffers require additional memory. PNG encoding starts after stream capture stops, reuses files for idle events, and removes each raw file after successful conversion. Analysis reuses decoded images for repeated file references. All resources belong to the short-lived diagnostic, not a production cache. Disk writes add diagnostic load and sampling gaps still fail analysis.

The recorder uses `SCStreamFrameInfo.displayTime`, converts its native system units with `CMClockMakeHostTimeFromSystemUnits`, and maps host time to UTC. The failed run showed idle sample-buffer PTS advancing far more slowly than callback arrival time, eventually exceeding the two-second alignment limit. Sample PTS is now retained only as a diagnostic. Missing or stale display timestamps still fail validation; arrival times are not substituted to manufacture coverage. Metadata includes display timestamps, arrival timestamps, complete/idle status, clock uncertainty, stream errors, and unusable events. It stops 750 ms after observing the saved build's `gpu-drawn` IPC file, with a hard 20-second capture deadline. The existing Cap helper still verifies normal editor close and terminates only owned processes.

Before downloading or launching Cap, a 4.6-second native self-test changes the center stripe blue → green → blue. Analysis requires the expected pixels in all three timestamped phases, allowing 80 ms after each color change. This checks retention beyond the former two-second buffer, the pixel format, stream updates, and clock alignment on the actual runner. It cannot be executed on Windows. After Cap completes, the runner allows up to 120 seconds for the recorder to finish converting its retained pixels to PNGs.

## Evidence and interpretation

Analysis keeps complete frames and excludes idle notifications from pixel coverage. Idle notifications must reference the preceding complete frame's file; their repeated timestamps are valid because no new frame was generated. Complete-frame timestamps must still increase strictly. Analysis requires a separately observed preview/GPU callback interval of at least 50 ms, at least two pattern-bearing complete frames from 20 ms after the preview callback through 25 ms before the GPU callback, and at least two from 50–600 ms after the GPU callback. Frames are attributed using software callbacks and captured presentation times, not physical display scanout. Missing coverage, duplicate complete-frame timestamps, an unstable or wrong owned window, an actual-frame sampling gap above 50 ms, stream errors, or unusable stream events make the result inconclusive. Idle notifications cannot fill actual-frame gaps. No retry or sample omission turns an incomplete recording into a passing visual claim.

The inspected crop is the whole owned editor window. The static source pattern must remain present in every sampled frame between the observed preview and post-GPU samples; a loss is flagged as a possible visual discontinuity. Per-frame pixel differences against the final editor crop are saved as diagnostics. They include UI chrome, so a difference does not automatically identify an image flash, and zero sampled differences cannot rule out shorter unsampled events.

A green collection job means `evidence-ready-for-review`, not “flash-free.” Manual inspection of `recording/transition-filmstrip.png` and the raw frame sequence is still required. This samples a virtual macOS display and cannot prove behavior on a physical consumer Mac, every image or preset, or events between captured samples. Recording adds load, so this job's draw times are not performance measurements.

Artifacts retain all captured PNGs, recorder metadata, original Cap input PNG, Cap logs, package/source provenance, calibration evidence, per-frame diagnostic differences, and a filmstrip. Read `transition.json`, `recording/recording.json`, `recording/analysis.json`, and `report.md` alongside the images. The production reviewer fixes and the CI evidence commits remain on separate branches.

## Local checks

Install the pinned Python dependencies in an isolated environment, then run `python scripts/screenshot-transition-check/test-analysis.py`. The tests use synthetic PNGs and mocked processes; they do not launch Cap. Native Swift compilation, actual capture, and the blue/green calibration require the macOS job. The workflow has an eight-minute limit and retains partial evidence on failure where Actions permits upload.
